Metodologia

La detection è rule-based e combina più livelli di evidenza raccolti durante la pipeline. L'obiettivo non è indovinare la tecnologia da un solo indizio, ma accumulare marker coerenti per assegnare un framework primario, eventuali framework secondari, un CMS e un livello di confidenza.

Criteri Di Detection

  1. Marker nell'HTML La homepage salvata viene ispezionata per cercare firme note nel markup o nello stato iniziale della pagina. Esempi:

    • __NEXT_DATA__ o id="__next" per Next.js
    • __NUXT__ o id="__nuxt" per Nuxt
    • drupalSettings per Drupal
    • wp-content, wp-json o wordpress per WordPress
    • themeDisplay, Liferay.ThemeDisplay o Liferay.Loader per Liferay
    • csrfmiddlewaretoken o __admin_media_prefix__ per Django
    • __VIEWSTATE o __EVENTVALIDATION per ASP.NET

  2. Meta tag e script inline Quando disponibili, vengono letti anche segnali già presenti nella homepage senza bisogno di eseguire altro codice:

    • meta generator o tag simili per CMS come WordPress, Drupal e Joomla
    • variabili globali o bootstrap inline come __NEXT_DATA__, self.__next_f, window.__NUXT__

  3. Header HTTP e cookie applicativi Per le homepage raggiungibili vengono raccolti anche alcuni header selettivi e i nomi dei cookie di risposta. Questi segnali non bastano da soli a spiegare tutta la tecnologia del sito, ma aiutano molto sui framework server-side e sugli stack backend. Esempi:

    • X-AspNet-Version, X-AspNetMvc-Version, ASP.NET_SessionId per ASP.NET
    • laravel_session per Laravel
    • csrftoken, django_language, server: gunicorn o server: uwsgi per Django

  4. Marker negli URL degli asset Gli URL di script e fogli di stile vengono letti come segnali strutturali. Questo aiuta soprattutto per CMS e framework con percorsi standardizzati. Esempi:

    • wp-content, wp-includes, elementor, woocommerce per WordPress
    • /_next/ per Next.js
    • /_nuxt/ per Nuxt
    • /o/, __liferay__ o Liferay.Loader per Liferay
    • /static/admin/ o /admin/js/ per Django
    • WebResource.axd, ScriptResource.axd o /aspnet_client/ per ASP.NET
    • /livewire/livewire.js o /_ignition/ per Laravel

  5. Marker nel contenuto dei bundle JS Quando i bundle vengono scaricati, il detector cerca simboli e stringhe tipiche delle librerie realmente eseguite:

    • React, react.production, createElement
    • Vue, __VUE__, createApp(
    • @angular, zone.js
    • jQuery, $.fn.jquery
    • bootstrap, data-bs-toggle
    • bootstrap-italia, --bootstrap-italia-version
    • Liferay.Loader, Liferay.ThemeDisplay, Liferay.Portlet, @liferay/
    • django.jQuery, csrfmiddlewaretoken
    • __doPostBack, Sys.WebForms.PageRequestManager
    • livewire, laravel

  6. UI framework da CSS I CSS vengono usati soprattutto per intercettare framework di presentazione o builder:

    • Bootstrap
    • Bootstrap Italia
    • Tailwind CSS
    • Foundation
    • UIkit
    • Elementor

Come Viene Assegnato Il Risultato

  1. Catalogo di fingerprint Le firme sono organizzate per tecnologia, famiglia (cms, framework, ui, library), fonte, peso e intensità del segnale. In questo modo un marker strutturale come __NEXT_DATA__ vale più di un indicatore generico come createElement.

  2. Scoring pesato Le evidenze non vengono più conteggiate in modo piatto: sono deduplicate per sorgente e marker, poi pesate in base alla loro affidabilità. Questo riduce il rumore dei bundle terzi e delle librerie trasversali come jQuery.

  3. Framework primario Viene scelto il candidato con lo score più affidabile, applicando tie-break semantici:

    • un CMS strutturale prevale su una libreria generica con segnali deboli
    • Bootstrap Italia prevale su Bootstrap
    • i soli UI framework non forzano automaticamente un framework applicativo primario

  4. Framework secondari Gli altri framework con marker presenti rimangono come secondari. Questo è utile nei siti ibridi, per esempio WordPress con widget React o pagine che caricano jQuery e Bootstrap.

    Quando compaiono marker specifici di Bootstrap Italia, il detector privilegia questa etichetta e non la fa ricadere automaticamente nel bucket generico Bootstrap.

  5. CMS primario Viene assegnato separatamente quando esistono marker forti di piattaforma editoriale.

  6. Indizi backend In parallelo al framework primario, il detector produce anche backend_hints: indizi non invasivi su linguaggi o runtime osservabili pubblicamente, come PHP, Python, Node.js o Java. Sono classificati come hint e non come verita assolute, perche molti siti nascondono o riscrivono i propri header dietro proxy e CDN.

  7. Confidenza

    • high quando il primario ha score alto o più evidenze forti
    • medium quando esiste un candidato credibile ma con segnali meno strutturali
    • low quando non ci sono segnali robusti o il risultato resta debole

Come Leggere Gli Incroci

Il report distingue volutamente tre piani diversi:

  • CMS primario, per piattaforme editoriali come WordPress, Drupal, Joomla o Liferay.
  • Framework applicativo primario e secondario, per tecnologie che emergono da markup, header, URL o bundle JS.
  • UI framework, per librerie di presentazione rilevate soprattutto da CSS, URL dei CSS e alcuni marker di contenuto.

Questa separazione evita di far competere concetti diversi. Un sito puo essere WordPress come CMS, caricare componenti React in un plugin, usare jQuery per funzionalita storiche e avere Bootstrap Italia o Tailwind CSS come layer di presentazione. In quel caso il CMS descrive la piattaforma editoriale, React o jQuery descrivono librerie applicative osservate, mentre Bootstrap Italia o Tailwind CSS descrivono il sistema di interfaccia.

Per questo l'incrocio tra UI framework e CMS/framework va letto come co-occorrenza osservata sulla stessa homepage, non come rapporto di dipendenza tecnica. La domanda a cui risponde e: "quando vediamo un certo UI framework, quale piattaforma o framework primario vediamo nello stesso record?". Non risponde invece a: "quel CMS e stato sviluppato con quel UI framework?" oppure "tutto il sito usa solo quella tecnologia?".

Nei dati di dettaglio i campi utili sono:

  • cms_primario, quando il detector trova una piattaforma editoriale forte.
  • framework_primario, quando il detector trova un framework applicativo prevalente.
  • framework_secondari, quando altri framework o librerie hanno marker presenti ma non prevalenti.
  • ui_frameworks, che puo contenere zero, uno o piu framework di interfaccia.

Quando si costruisce una tabella UI x CMS/framework conviene usare cms_primario come prima scelta e, se manca, usare framework_primario. Se mancano entrambi, il record resta in un bucket "nessun primario": non significa che il sito non usi tecnologie, ma che i marker raccolti non sono sufficienti per assegnare una piattaforma primaria affidabile.

Perche` Tailwind Compare Poco

Tailwind CSS viene rilevato come UI framework, non come framework applicativo. Nel detector attuale il marker forte per Tailwind eprudente: viene cercata la stringatailwind` negli URL dei CSS. Questa scelta riduce i falsi positivi, ma non prova a riconoscere Tailwind da ogni possibile classe utility nel markup.

Il motivo emetodologico. Classi comeflex, grid, hidden, container, text-omt- possono comparire anche in codice custom, in altri framework CSS o in CSS compilati e rinominati. Cercarle in modo aggressivo aumenterebbe il numero di occorrenze, ma renderebbe meno affidabile il risultato. Il report preferisce quindi contare Tailwind solo quando c'e un indizio abbastanza esplicito, per esempio un asset CSS che mantiene il nome tailwind.

Questo significa che le occorrenze Tailwind sono da leggere come casi ad alta evidenza nominale, non come stima esaustiva di tutti i siti che potrebbero avere CSS generato con Tailwind. In particolare, un sito che compila Tailwind in un file generico come style.css, senza lasciare marker nel nome dell'asset, puo` non essere classificato come Tailwind.

Il fatto che Tailwind appaia spesso insieme a WordPress e ad altri UI framework non e contraddittorio: WordPress puo usare temi o plugin che includono un CSS Tailwind, e la stessa homepage puocaricare anche Bootstrap Italia, Elementor o Bootstrap. Il campoui_frameworks e quindi multi-valore proprio per rappresentare questi casi.

Perche` Angular E React Possono Comparire Insieme

La co-occorrenza Angular + React puo sembrare strana se la si legge come "il sito e stato scritto sia in Angular sia in React". Nel report, pero`, la heatmap non dice questo. Dice solo che nello stesso record sono stati normalizzati marker di Angular e marker di React, indipendentemente da quale sia primario e quale secondario.

Ci sono varie ragioni plausibili:

  • Un'applicazione principale Angular puo` caricare widget, librerie o componenti embedded che includono React.
  • Un CMS o un portale puo` esporre pagine, plugin o bundle diversi nella stessa homepage.
  • Alcuni servizi terzi incorporati nella pagina possono portare con se` bundle React.
  • Nei bundle minificati possono rimanere marker React generici, come react, react-dom o createElement.
  • La homepage puo` essere un contenitore ibrido, con parti legacy e parti moderne caricate insieme.

Per ridurre il rumore, React non diventa automaticamente primario quando compare un marker generico. Marker come createElement hanno peso basso; segnali piuspecifici comereact-dom, react.productiono__react pesano di piu. Angular, invece, diventa piu facilmente primario quando emergono marker piu caratteristici come ng-version, @angular o zone.js.

Quindi una riga Angular + React va interpretata cosi: **Angular e spesso il candidato applicativo prevalente; React e spesso un segnale secondario osservato nei bundle o in componenti caricati dalla pagina**. E un ottimo elenco per una verifica manuale o per capire quali siti hanno front-end ibridi, ma non va trasformato automaticamente in una conclusione architetturale forte.

La differenza tra conteggi simili ma non identici puo` dipendere anche dal livello a cui si conta:

  • la heatmap usa framework primari e secondari gia` normalizzati;
  • technology_scores contiene anche segnali grezzi sotto soglia;
  • i dati pubblicati possono cambiare se si rilancia il detector o si modifica la soglia di scoring.

Per confronti ripetibili equindi meglio dichiarare sempre quale campo si sta usando:framework_primario+framework_secondariper le co-occorrenze normalizzate,technology_scores` per audit e debug dei marker.
